# MultiVision plan2: session-local camera management

Source: the Driver's current requirements in this conversation, which explicitly supersede the persisted stable-ID camera-binding direction of ADR-0001 for this plan. ADR-0001 is not modified by this plan; the divergence and its consequences are recorded in the validation contract.

The plan replaces persisted camera bindings and persisted calibrations with an explicit session-local camera inventory. It supports up to four simultaneously open/displayed cameras, while allowing more discovered devices to be closed and opened during the same `main.py` run. No task may require restarting `main.py` for rename, close, or reopen operations.

Shared contracts: [plan2-validation-contract.md](plan2-validation-contract.md).

1. Record the plan2 scope and compatibility boundary in implementation-facing documentation without editing ADR-0001: session-local `camera-N` slots, current-session capture-index authority, no camera-name/calibration persistence, four simultaneously active cameras, CLI-only management, and no hot-plug-in support; verify every later task links to the shared validation contract.
2. Define an in-memory session camera model and registry that separates immutable session slot identity (`camera-0`, `camera-1`, etc.) from mutable display name, capture index, open/closed/unavailable state, frame metadata, calibration state and overlay association; verify default naming, unique rename validation, deterministic ordering and the rename/close/reopen calibration lifecycle. See the [shared validation contract](plan2-validation-contract.md).
3. Replace persisted stable-ID discovery for the runtime opening path with one startup enumeration of currently connected OpenCV capture indexes, producing deterministic session slots and enough metadata for display and diagnostics; preserve explicit errors for malformed probes and do not persist or use a numeric index across sessions; verify enumeration does not silently substitute a different device for an existing session slot. See the [shared validation contract](plan2-validation-contract.md).
4. Refactor camera runtime ownership so all selected session cameras are opened once at startup, all active cameras are continuously displayed up to the four-camera limit, and close/open operations release or acquire handles without rediscovering or remapping session slots; verify persistent handles, frame counters, cleanup, active-camera limits and explicit failure when opening a closed or unavailable slot fails. See the [shared validation contract](plan2-validation-contract.md).
5. Implement disconnect handling for cameras present at startup: release the affected handle, mark its session slot unavailable, invalidate its calibration and reject spatial operations; explicitly leave hot-plug-in unsupported so a device connected after startup is not silently added; verify unplug/error paths never fall back to another capture index. See the [shared validation contract](plan2-validation-contract.md).
6. Add service-level camera management capabilities for listing session slots, renaming a slot, closing it and reopening it, with atomic state transitions and deterministic responses; verify renaming preserves the slot's live frame, calibration and overlay, while close/reopen clears calibration and any overlay owned by that camera. See the [shared validation contract](plan2-validation-contract.md).
7. Extend the local API and thin CLI with the session-management operations (`cameras list`, `cameras rename`, `cameras close`, `cameras open`) while keeping camera control out of Pygame and avoiding any independent camera opening in the CLI; verify commands work against a running service without restart, reject unknown/duplicate names and return explicit state errors. See the [shared validation contract](plan2-validation-contract.md).
8. Update the Pygame display runtime to render every active session camera in deterministic slot order, show current names and lifecycle/calibration state, and rebuild layouts safely after rename, close, reopen or disconnect; verify up to four active previews are visible simultaneously and closed slots do not retain stale preview surfaces. See the [shared validation contract](plan2-validation-contract.md).
9. Preserve one shared click path for every session camera so a click resolves the current slot/name, maps preview coordinates to that camera's native coordinates and uses only that camera's current calibration; verify renaming does not change the selected calibration and clicks cannot use another camera's transform. See the [shared validation contract](plan2-validation-contract.md).
10. Add the uncalibrated-click visual state: when a valid click lands inside an available but uncalibrated camera preview, retain the normal point failure and draw a red frame around that camera's Pygame preview; keep the frame while the camera remains uncalibrated, clear it on successful calibration or camera close/reopen, and do not draw it for clicks outside the preview or for another camera; verify this independently from projector overlays. See the [shared validation contract](plan2-validation-contract.md).
11. Adapt calibration and verification to session camera slots, keeping calibration records in memory only and associating them with the session slot rather than persisted device IDs; verify calibration succeeds and is independently used for each camera, rename preserves it, close/reopen resets it to uncalibrated, and unavailable cameras fail closed. See the [shared validation contract](plan2-validation-contract.md).
12. Replace the old persisted camera-binding/calibration startup path with the plan2 session model while retaining only explicitly supported non-camera configuration such as projector resolution and thresholds; ignore or safely invalidate legacy camera bindings and calibration records rather than applying them to new slots; verify a clean session has default `camera-N` slots and no stale spatial authority. See the [shared validation contract](plan2-validation-contract.md).
13. Add focused deterministic tests for session models, discovery snapshots, slot naming, four-camera limits, rename preservation, close/reopen invalidation, malformed state and legacy-data rejection, using injected capture seams rather than physical devices; verify the tests do not rely on capture-index stability across process restarts. See the [shared validation contract](plan2-validation-contract.md).
14. Add runtime and service integration tests for simultaneous ownership, dynamic close/open, disconnect handling, frame retention, API responses and CLI requests; verify no operation opens a camera twice, no closed camera is read, no unplugged camera is substituted and `main.py` need not restart for management operations. See the [shared validation contract](plan2-validation-contract.md).
15. Add display and pointing regression tests for dynamic layouts, current-name resolution, per-camera calibration selection, preview-coordinate conversion, uncalibrated red framing, successful projector pointing and overlay clear/replace semantics; verify GUI and API/CLI native-coordinate requests share the same session camera and geometry authority. See the [shared validation contract](plan2-validation-contract.md).
16. Update the manual hardware smoke procedure for plan2: start with all currently connected devices, identify each `camera-N` from its live preview, rename or close slots through the CLI, reopen a slot without restarting, calibrate at least two independently aimed cameras, confirm uncalibrated clicks are red-framed, unplug one camera to verify explicit unavailability, and record that a later hot-plug is intentionally unsupported; do not claim physical acceptance without target-Mac observations. See the [shared validation contract](plan2-validation-contract.md).
17. Run the complete deterministic suite and perform an integration review against this plan, the validation contract and the current code: remove stale persisted-binding assumptions, duplicate camera authorities, silent index fallback and restart-only management paths; verify the clean project-root command passes and report remaining hardware-only uncertainty without modifying ADR-0001 or claiming hardware success. See the [shared validation contract](plan2-validation-contract.md).
