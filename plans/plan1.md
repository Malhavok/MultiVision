# MultiVision MVP0 implementation plan

Source: `docs/ADR-0001_ MultiVision MVP0 Architecture and Implementation Contract.md` (accepted).

Shared contracts: [plan1-validation-contract.md](plan1-validation-contract.md).

The plan implements MVP0 only. Hardware checkpoints remain manual and must not be reported as passed by automated agents.

1. Establish a small `multivision/` Python 3.12+ package and `tests/` layout around the existing `camera.py` and `main.py`, adding central configuration, explicit runtime/status types, domain errors and hardware seams without changing the accepted ADR or introducing a second source of truth; verify the package imports and `.venv/bin/python -m unittest discover -s tests` runs.
2. Replace numeric-index camera identification with a discovery boundary that exposes stable device identifiers where the platform provides them, reports device metadata and keeps platform-specific macOS enumeration behind the boundary; add deterministic fake-discovery tests proving unavailable devices are reported rather than silently substituted.
3. Add persistent logical camera bindings and configuration loading/saving for names such as `overhead`, `side-left`, `side-right` and `macbook`, including malformed-file and missing-device handling; verify bindings round-trip and a changed numeric index cannot inherit another device's binding.
4. Implement the persistent camera runtime that opens each available bound device once, owns every capture handle in the service, continuously retains the latest usable frame with a counter or timestamp, and exposes explicit unavailable/error status; verify with fake capture devices that snapshots do not reopen cameras and all handles release on shutdown.
5. Implement pure coordinate-space and homography primitives for preview-local-to-camera-native conversion, camera-to-projector and projector-to-camera transforms, finite/bounds checks and projection round trips; verify scaled and letterboxed previews, padding rejection, degenerate matrices, out-of-region points and projector bounds using synthetic data.
6. Implement a deterministic projector calibration-pattern model and renderer-facing marker-corner metadata using 9–12 uniquely identified AprilTag-family markers over the usable output area; verify every marker corner has a stable projector-native coordinate and pattern generation does not depend on camera output or UI layout.
7. Implement per-camera fiducial detection and correspondence assembly using all valid marker corners, with `cv2.aruco` and `DICT_APRILTAG_36h11` behind a testable detector boundary; verify recorded or synthetic frames identify IDs, ignore unknown/invalid detections and preserve each camera's independent correspondences.
8. Implement homography calibration from detected correspondences with RANSAC, inverse transform storage, reprojection metrics and a configurable spatial-coverage/valid-region quality check; verify perspective recovery, noisy points, outliers, insufficient coverage and refusal of weak or invalid calibration.
9. Implement calibration persistence and verification state transitions, storing stable camera ID, camera/projector resolutions, version, matrices, metrics and timestamp; verify restart-loaded calibrations begin `UNVERIFIED`, resolution changes and failed verification become `STALE`, successful verification becomes `CALIBRATED`, and spatial operations fail closed for all invalid states.
10. Implement the Pygame main-thread display runtime with live previews for active cameras and a projector surface, showing logical name, connection/calibration state, native resolution and available quality metrics; verify rendering uses latest frames, preserves camera ownership and keeps projector rendering/calibration pattern separate from geometric truth.
11. Implement the single shared point-and-overlay service path from preview click or native camera coordinates through region validation and camera-to-projector mapping to a red-circle overlay, plus clear/replace semantics; verify GUI, API and CLI callers use the same path and click results are rejected explicitly for every ADR failure condition.
12. Implement the persistent MultiVision service lifecycle and local FastAPI endpoints for health, camera status/snapshot, calibration/calibration verification/status and point/clear-overlay operations, with request validation and explicit error responses; verify endpoint behavior with fake devices and no physical cameras while keeping FastAPI out of camera/renderer ownership.
13. Implement the thin executable `multivision` CLI client for status, camera listing/binding, calibration, verification, snapshots, camera-space point requests and overlay clearing; verify it sends requests to the running service, returns useful non-zero failures and never opens cameras, initialises Pygame or recalculates homographies itself.
14. Replace the prototype `main.py` capture-and-exit flow with the integrated service/UI startup and orderly shutdown, preserving main-thread Pygame event processing and worker/API lifecycle rules; verify ordinary startup, unavailable-camera startup and shutdown with fakes, and provide exact manual commands/expected observations for a one-camera screen-or-printed-sheet smoke check and for cross-camera checks across all currently configured cameras without claiming hardware success; do not hard-code a camera count.
15. Run the complete automated suite and perform an integration review against ADR-0001, removing stale prototype paths, duplicate geometry/state authorities, silent fallback behavior and unrelated changes; verify deterministic tests pass from a clean project-root invocation and record any remaining hardware-only acceptance work without modifying the ADR.
